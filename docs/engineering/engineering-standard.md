# TapScene 点演工程规范与 GitHub 变更治理

版本：0.1 提案稿

日期：2026年10月9日

适用基线：点演产品规格 v0.1，F01–F29 与 A01–A16

产品英文名：TapScene；中文名：点演；仓库：[gluttonsama-cloud/TapScene](https://github.com/gluttonsama-cloud/TapScene)

本规范用于把点演做成可维护、可测试、可恢复的产品。提案、接口、代码、测试和发布采用同一条可追溯变更链。文档通过 PR 被接受后成为工程约束；它不代表仓库设置已启用，也不代表任何功能、测试或性能目标已完成。

本次入库处于规范 Proposal 阶段，没有产品实现、合并或部署。仓库已有用户初始化的 Apache-2.0 LICENSE；本 PR 提供产品 Markdown 基线、需求追溯、规范、模板与真实最小文档 CI。当前远端与保护证据见[入库适配记录](repository-adaptation.md)，CI 边界见[文档 CI](../testing/docs-ci.md)。后文产品级检查名和治理目标仍是待落地要求，不能当作已启用设置。

## 1 不可退让的交付原则

1. **产品主流程可独立使用。** Android 手机端应实际完成导入、整理、编辑、脱敏、复核、交付；页面不能靠演示人员口头解释、后台手动改库或预录视频补齐。
2. **前端直接支持当前任务。** 项目、步骤、问题、进度、操作和恢复入口优先。首屏不放宣传口号、虚构数据看板、功能展示卡或与当前操作无关的营销文案。
3. **每个可见动作有真实后果。** 不允许空 onClick、永远成功的假请求、定时器模拟完成、显示已保存但未持久化、调起分享页就显示已送达。未实现能力不作为可用按钮展示；暂时不可用的已实现能力须给具体原因和恢复条件。
4. **成品只包含安全派生资产。** 原录屏、原始 OCR、真实源路径、原音轨与编辑历史不得混入观看包、AI 包、网页资源、日志或测试附件。
5. **有限模拟边界必须真实。** 不调用原 App 业务接口，不收集观看者真实凭据，不把作者编排、OCR 候选或未录制结果写成已验证事实。
6. **隐私和访问失败时拒绝放行。** 缺复核、复核失效、缺媒体、断边、非法路径、撤销状态不明等不能静默降级成成功。
7. **主干只接收可解释、可复查的变更。** 包括 proposal、RFC、ADR、说明和 CI 配置，全部经 PR；不因“只是文档”直接改 main。
8. **进度按证据表达。** “已设计”“已实现”“自动测试通过”“真机通过”“可发布”是不同状态。没有执行记录时只写“未运行”，不写“预计通过”。

产品级不等于一次实现全部功能。允许先发布范围明确、可独立完成真实任务的窄切片；发布说明准确列出该版本支持范围与限制，不宣称已经完成产品规格 v0.1 的全部 P0。测试夹具、mocks 和样例项目可以用于研发，但不得进入生产路径冒充真实数据、请求或结果。P0 目标的增删改仍经 proposal PR 接受，不能靠修改措辞、隐藏入口或改名为完成来消失。

## 2 从需求到版本的最小追溯链

### 2.1 ID 和材料

沿用产品规格的 F01–F29，不重新发明一套功能编号。具体可验证规则用后缀，例如 F14-AC01；统一验收样例沿用 A01–A16。额外工程约束可用 ENG-001，缺陷用 BUG-编号。

一个变更至少能沿以下链条回查：

需求 ID → 提案 PR → 必要时的 RFC 与 ADR → 实现 PR → 测试与证据 → 发布版本和变更记录。

- **Proposal** 说明解决什么、谁使用、范围、非目标和如何验收。产品范围改变必须先有提案 PR。
- **RFC** 仅用于跨模块接口、数据契约、关键技术取舍、安全边界、迁移或外部服务变化。可以是同一提案中的“技术方案”章节，不要求复制一份文档。
- **ADR** 记录被接受的长期决定、替代方案与代价，通常一页足够；小修复不强制写 ADR。ADR 不能代替尚未通过的 proposal，也不能倒填成“当时已批准”。
- **实现 PR** 只做已接受范围；问题暴露新取舍时补提案或修订 RFC 后继续。低风险文案、局部修复可在实现 PR 正文承载微型 proposal。
- **测试证据** 绑定最终待合并提交、环境、素材及运行结果；验收截图不替代实际行为测试。
- **版本记录** 列出需求 ID、合并 PR、已知限制、schema/adapter 版本、迁移和回退方式。

不为每个 ID 单独建 Issue；一个任务卡可覆盖相关的 2–3 个验收项。一个小改动不必走三个独立文档 PR。需要冻结的是风险和接受标准，不是文档数量。

### 2.2 最小需求记录

每项记录以下字段：需求 ID；来源与理由；P0/P1；负责人；验收条件；依赖；关联 proposal/RFC/ADR；实现 PR；测试证据；目标版本；当前状态。

状态为：待澄清、待接受、已接受待实现、实现中、待验收、已验证、已发布、推迟或取消。“已验证”必须标明验证范围，不能因为一条单元测试通过就把整个 F14 标为完成。

例如 F14-AC01：修改遮挡位置后，相关图片、区域裁切、封面及视频派生内容的复核失效；旧发布版本不变；输出被重新复核前不可交付。证据需覆盖摘要变化、依赖失效、拦截行为和旧版本不变四项。

### 2.3 建议目录

- docs/product/：产品规格、需求矩阵、文案与页面行为。
- docs/proposals/：已编号的方案提案及修订记录。
- docs/adr/：已接受或被替代的架构决定。
- docs/contracts/：数据包、schema、坐标、时间轴和 API 合同。
- docs/testing/：测试计划、设备矩阵、发布验证报告；原始大量产物放有期限的制品存储。
- docs/operations/：运行手册、告警、迁移、恢复及事故记录。
- docs/engineering/：本规范的唯一权威源；仓库根 AGENTS.md 只提供 AI 执行入口并链接此处。
- .github/：PR 模板、Issue 模板、贡献规则和 CI；有真实负责人后再补 CODEOWNERS。
- tests/fixtures/：获得授权、去标识或合成的测试样本及预期答案，不放真实用户素材。

产品目录仍是建议，不预先决定具体技术栈；本次已存在文档路径及最小检查入口见根 README。

### 2.4 AI 执行入口 AGENTS.md

仓库根目录建立 AGENTS.md，写明每次任务必须先读当前需求、相关提案与 ADR，先列变更范围、风险、检查和回退；禁止直接 main、未经授权合并或部署；要求同步需求追溯并留存真实检查结果，交付说明遵循简洁 PR 风格。它引用本规范、产品规格、契约和实际构建说明，不复制整份规范制造版本漂移。每项生产 UI 行为都须真实实现，不能用 mock 方案或截图交差。

随本提案提供并落位根 AGENTS.md，状态随本 Proposal PR 待接受。CODEOWNERS 只在真实账号与职责核实后添加，模板不预填人名。

## 3 GitHub 分支与 PR 工作方式

### 3.1 一项任务一个短分支

- 默认分支 main，始终可构建且不接受直接业务提交；不设置长期 develop 分支。
- 分支名采用 docs/F14-review-contract、feat/F17-history-back、fix/BUG-012-import-isolation 等可读形式。
- 开始有可供讨论的差异后即开 Draft PR，尽早暴露设计与风险；没有差异时先保留提案任务，不伪造空进度。
- 一个 PR 只解决一个明确问题。一般以不超过约 400 行人工编写变更为拆分提示，生成文件、锁文件和测试样本单列；这不是可被机械利用的硬额度。
- 跨层垂直切片允许同 PR 修改领域、存储、界面和测试，前提是仍能独立审查与回退。不要按行数拆成无法编译的中间状态。
- 堆叠 PR 只有在顺序与依赖明确时使用，先合基础层，再调整上层基线并重跑检查。
- PR 标题采用英文类型与中文描述，例如 `docs(ENG-001): 简化变更说明`；类型按实际变更使用 docs、feat、fix、chore 等。正文只写具体变更与必要需求关联，不附核验、测试、待确认或 SHA 清单。
- 默认 squash merge，标题保留需求 ID。合并后删除已完成任务分支；发布标签不得移动或覆盖。

本仓库已支持 GitHub 原生 Draft，由 GitHub 阻止草稿合并，转为 ready 后才能进入正式审查。ci/gate 只汇总真实内容检查，不重复实现 Draft 或标题正文策略；元数据修改不触发内容重测。若未来环境不支持原生 Draft，须另行设计并验证等效保护，不能只贴“draft”标签冒称已受保护。[GitHub PR 文档](https://docs.github.com/en/pull-requests/reference/pull-requests)

### 3.2 main 的目标保护配置

仓库建立后，优先建立一套可读的 branch ruleset；传统 branch protection 也可，但避免多套重复规则造成难以解释的限制。目标如下：

- main 的每项变更必须关联 PR。
- 必需检查 ci/gate 通过，分支相对 main 最新；稳定后如确有多人并行需求再评估 merge queue。
- 所有阻断审查问题已处理；不允许作者用“已解决”代替给出修复证据。
- 禁止强制推送，禁止删除 main；不授予日常开发绕过权限。
- 如使用传统保护，明确检查管理员也受保护，而非依赖默认值。
- 默认只开放 squash 合并，维持清晰线性历史。
- 标签发布另设保护，防止已分发版本改指向；若具体套餐不支持该项，记录差距与人工控制。
- CI、权限与发布流程变更作为高风险变更专门审查；不能在修改业务逻辑的 PR 中悄悄删检查。

这些是项目目标配置，只有读取实际配置并验证后才能标为启用。GitHub 的保护规则、绕过行为和 status check 选项有明确平台条件，不能仅凭仓库中出现 YAML 或 CONTRIBUTING.md 就认为 main 已受保护。[GitHub 分支保护文档](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

### 3.3 套餐与可用性必须实查

截至2026年10月9日查阅官方文档，公共仓库可在 GitHub Free 使用 branch protection 与 branch/tag rulesets；私有仓库通常需要适用的 GitHub Pro、Team 或 Enterprise 套餐。组织级规则、push rulesets、部署审批等又有自己的适用条件，不能把“有 ruleset”泛化成“所有功能均可用”。[GitHub rulesets 文档](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)

仓库创建后首先登记：owner 与仓库 URL、个人或组织、public/private、套餐、管理权限、Draft 可用性、保护规则、Actions 可用性与预算、检查来源、可用真实审查者、发布环境保护。

- 若私有仓库当前无法强制 main 保护，应报告“平台强制保护未就绪”。可准备 proposal 和分支，不宣称实现 PR 已满足本规范的合并门槛。
- 由用户选择升级适用套餐或其他可强制的安排；不得为了省费用自行把仓库公开。
- 本地 hook、口头约定、写在 README 中的规则不能等同服务器强制保护。
- GitHub 环境存在不等于部署审批存在。Free、Pro、Team 对某些私有仓库部署保护有额外限制，须单独核查；无法用原生审批时，发布者手动确认与最小权限凭据的流程也要真实执行并留记录。[GitHub 部署环境文档](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)

### 3.4 单人和多人审查都必须诚实

**只有一个真实 GitHub 参与者时：**

1. 仍然强制 PR、CI、最终差异复查和任务级验收。
2. 设置 require PR，必需独立 Approve 数量为 0，不设置一个实际无人能完成的审批要求，再靠管理员绕过。
3. 自查、AI 辅助审查、维护者确认和独立人类审查的实际状态保留在真实审查记录或必要测试文档，不强制写入每个 PR 正文。同一人可以承担多项职责，但不能包装成三个人，未进行的审查不得冒称完成。
4. AI 可以另轮检查安全边界、边界条件、测试遗漏和差异，但不得用虚假 GitHub 身份、虚构账号、代写他人 Approve 或机器人互批来制造独立性。
5. 高风险内容在发布前必须有逐项证据与责任人确认。若风险需要独立专业评审而实际无人具备能力，保留为发布阻断，而不是降低风险描述。

**有第二位实际合作者时：**

- 必需 1 位有合适权限、理解变更且不是 PR 作者的真实人员 Approve。
- 开启新提交使旧批准失效；必要时要求最新可审查推送由推送者之外的人批准。
- CODEOWNERS 只填写已同意承担职责、且具有所需权限的真实账号；安全导入、脱敏、鉴权、CI、迁移和发布路径明确责任人。
- 审查记录指出看了哪些内容、执行或复核了哪些测试、还剩哪些风险。“LGTM”不能替代关键行为证据。

GitHub 不允许 PR 作者批准自己的 PR；GitHub Copilot 的审查也不计入规定的人类 Approve 数量。允许 PR 但不强制 Approve 是 GitHub 支持的配置，不需要伪造第二人。[GitHub 审批规则](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews) [GitHub require PR 规则](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)

### 3.5 首次初始化与紧急情况

全新空仓库没有基线分支时无法正常比较 PR。用户创建仓库时可仅初始化最小 README 作为基线，记录这次一次性的建库提交；不借初始化直接导入产品代码或整套 proposal。之后 proposal 本身进入第一个 PR。

首个文档 PR 可同时带最小文档 CI，并在该 PR 首次运行成功后把 ci/gate 登记为必需，再合并。若平台无法完成该流程，明确记录 bootstrap 阻断，先解决设置，不用“先直接推 main，之后补 PR”代替。

事故修复也走小 PR，可缩短排队但不能跳过安全底线。真正需要调整保护时，由仓库负责人另行明确批准、记录原因与时限，完成后恢复并复核。AI 的编码或提 PR 权限不自动包含修改规则、合并、发版或上线权限。

## 4 开始与完成标准

### 4.1 Definition of Ready

进入实现前应满足：

- 对应需求 ID、边界、成功和失败行为明确，产品 proposal 已接受。
- 依赖接口与数据约束足够稳定；涉及兼容性、隐私或架构的 RFC/ADR 已明确。
- 页面至少定义空、加载、成功、失败、取消、重试、禁用和权限不足状态，不只有成功截图。
- 有确定性测试输入与预期答案，说明哪些可自动测、哪些必须真机或人工复核。
- 素材、图标、字体、模型和依赖的来源与使用权限明确。
- 能说明如何观测失败、如何恢复、如何回退；高风险项有责任人。
- 本次变更大小可审查；未知性能与平台能力已被标为调查项，不能混成实现承诺。

研究型 PR 可以为解决未知项而开始，但标题标为 spike 或 research，列出停止条件和输出证据，代码限定在实验分支或明确的 experiments 目录，默认不参与生产构建。复用实验结果须经独立产品化审查、测试和实现 PR；不得直接当生产实现合并后无人清理。

### 4.2 Definition of Done

每个实现 PR 完成须满足：

- 真实行为符合验收项，正常、边界、失败、中断、重复调用均有适用测试。
- 最终提交受影响范围内必要的格式、静态检查、构建、单元与集成测试通过，安全相关检查无阻断。
- UI 操作真正接入数据与任务状态；本地保存、失败恢复、删除后果与反馈一致。
- 已审查隐私流、日志、无障碍、文案、本地化资源和必要性能影响。
- 数据或接口变化同步 schema、兼容性说明与迁移测试；依赖变化更新锁文件与许可清单。
- 有最终差异审查及真实身份记录；必要检查的结果与未运行原因留在 CI 日志或测试文档，不能把未运行项记为通过。
- 用户文档、运维手册和需求追溯同步；已知风险有 owner、处理条件和时间，不留无归属 TODO。
- 发布影响和回退方式写清楚。合并不等于已部署，CI 通过不等于真机验收通过。

纯文档 PR 只做受影响文档的结构、链接与内容核对，不重复运行无关测试；需求追溯、技术事实与隐私检查仍须完成。

## 5 CI 必须成为有效门禁

### 5.1 分层检查

初期仅文档存在时先运行文档检查；每个实际模块进入 main 的第一个 PR 必须同时加入对应构建和测试。不能建立名称叫 test、内容却只是打印成功的占位任务。

建议稳定检查名如下，具体命令在技术栈冻结后填写：

- ci/policy：文件范围、契约变化、需求登记、文档格式与链接；PR 需求关联由模板与审查保留，Draft 状态由 GitHub 原生约束。
- ci/static：格式、lint、类型或编译静态检查。
- ci/unit：图结构、坐标、时间轴、校验器、摘要失效、历史栈和配额边界。
- ci/integration：存储事务、任务恢复、媒体管线、包导入与服务 API。
- ci/build：Android、Web、服务端与受信动画适配器的适用构建。
- ci/security：秘密扫描、依赖与许可策略、危险工作流及包安全回归。
- ci/e2e：适用的手机模拟器/浏览器关键流程，使用可重放合成样例。
- ci/gate：始终执行的汇总门禁，只在所有本次必需检查真实成功时成功。

按实际影响范围选择必要增量检查，优先直接核对运行和界面效果，不为测试数量或覆盖率增加冗余用例。纯文档只检查文档；检查器或 workflow 变化才跑对应检查器回归。共享 schema、构建、依赖、核心逻辑、隐私与数据变化须覆盖相应关联风险；不能因路径过滤漏触发把未测试算成功。

### 5.2 防止绿色假象

- 工作流用适用的 PR 触发事件；ci/gate 无条件汇总 needs 结果，失败、取消、预期任务缺失或意外 skipped 都拒绝通过。
- 不能在必需任务上用 continue-on-error、吞异常、空测试集或无条件 exit 0。
- 检查名唯一，绑定可信检查来源；不允许手动写一个同名成功 status 代替测试。
- 合并前核对当前 head、基线以及 GitHub 检查对应的 head 或 test-merge SHA；旧提交的绿色勾不构成新提交证据。冲突解决和更新基线后重测受影响范围。
- GitHub 会把某些 skipped/neutral 结果视为满足状态检查，因此项目的 ci/gate 要更严格；不要把平台合并按钮可点当全部测试已执行。[GitHub status check 故障排查](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)
- 测试随机失败要记录种子、重现条件和负责人；重跑成功不抹去失败。安全/隐私用例不能隔离后放行；非关键 flaky 用例临时隔离须有期限与补偿测试。
- 覆盖率用于暴露缺口，不能替代 A01–A16。先建立基线再冻结模块阈值；关键拒绝路径必须有明确用例，不用虚构“100% 已覆盖”。

门禁变更只验证受影响的成功、失败、取消、缺失和跳过分支，以及必要的路径分流；不重复编写 GitHub 原生 Draft 规则测试。合并前核对原生 Draft、需求关联及保护实际状态。不要为测试而把真实破坏提交直接推到 main。

### 5.3 CI 安全与费用

PR 测试只用最小只读权限，不携带生产部署、邮件、存储或签名秘密。第三方 Action 固定到审核过的完整 commit SHA，依赖固定锁文件；不在带写权限或 secrets 的工作流中 checkout 并执行不可信 PR 代码。尤其不把 pull_request_target 当普通测试入口。[GitHub Actions 安全说明](https://docs.github.com/en/actions/reference/security/secure-use) [GitHub pull_request_target 风险说明](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)

设并发取消、超时、制品期限与费用告警。真机测试可以独立于每次 PR 的快速 CI，但版本候选必须执行。所有 CI 日志、截图、转码视频和失败包使用安全样例；不能为调试自动上传用户源素材。

## 6 点演的产品级测试合同

### 6.1 可重复输入与独立答案

建立固定校园活动报名样例，覆盖成功、名额已满、取消、汇合、显式回访、同页异态、无触点录制、作者编排、通知及视频。记录样例版本、哈希、产生方式和授权。预期状态与真实事件来自样例 App 或人工标注，不能由被测 OCR/分段器给自己出答案。

修复缺陷时优先复用能复现问题的现有用例；确有覆盖缺口才新增最小必要回归，验证修复前失败、修复后通过。不删除仍有价值的既有测试。功能测试使用合成数据；获得许可的真实录屏用于补充泛化验证，并按最小范围存放，不能默认进入公开 GitHub 或长期 CI 制品。

### 6.3 架构风险门禁的关联

独立架构风险审查中的 G01–G10 作为上述测试的风险索引，保留在同一验收矩阵，不再建立一套平行进度表：

- G01：本地模型与所有依赖的出站行为，关联 A12；断网能用不等于零遥测。
- G02：实际输出字节、文本、坐标、处理器版本与复核摘要绑定，关联 A04/A05/A12。
- G03：恶意归档、JSON 和解码资源预算，关联 A10/A16；导入模块开工前冻结条目数、深度和像素限额。
- G04：到期撤销覆盖 GET、HEAD、Range、条件请求、缩略图、旧地址、缓存和断点，关联 A09。
- G05：数据库/文件阶段提交和任务幂等恢复，关联 A08/A11；区分系统回收与 force-stop 后重开。
- G06：各端同一合法/非法语料与 schema 语义一致，关联 A13–A16；原文件哈希与语义摘要分开。
- G07：真实设备的有界媒体管线、内存、临时磁盘、热与电量，关联 A11；性能阈值须先冻结。
- G08：并发配额、上传事务、跨账号管理与幂等发布，关联 A08/A09。
- G09：不可信数据与受信执行模板隔离、播放器异步竞态，关联 A02/A13–A16。
- G10：真实 PR 审查、当前提交证据与发布判断，关联本规范第 3、5、11 节。

门禁依据与详细反例见[质量与安全门禁](../testing/quality-gates.md)。任何具体架构选型仍以已接受 RFC/ADR 为准；本规范不因引用风险索引而宣称已完成这些测试。

### 6.4 类型和边界测试

- 单元及性质测试：稳定 ID；排序不改连线；坐标有限且范围合法；源毫秒与输出帧只转换一次；总帧数与重叠转场一致；重复访问有独立 visitId。
- 契约与黄金样例：同一包在 Android、Web 和 Remotion 适配器中保留一致路径语义；schema 不一致明确拒绝，不忽略关键字段后猜测执行。
- 模糊与恶意输入：JSON 体积/深度、极端数字、NaN/Infinity 等非法表示、Unicode/大小写路径冲突、符号链接及媒体解码失败；解析、解压和解码都有资源限额。
- 中断注入：导入、分析、烘焙、导出、上传和迁移逐阶段杀进程、取消、断网、重试；事务边界保证旧数据完好。
- UI 与真机：小屏、长屏、横屏观看、字体放大、系统返回、多次点击、旋转、后台恢复、权限拒绝、登录取消、视频失败。
- 服务端集成：统一可信时钟、过期边界、撤销与资源请求竞态、重试幂等、配额、缓存策略；撤销后不因 CDN 直链绕过授权。

### 6.5 性能证据

产品规格中的 40 状态、80 边、素材容量、视频时长和包大小均是设计约束，必须测边界和超限一单位。兼容 Android 最低版本、机型、浏览器范围和性能阈值在小样后冻结，不在本规范虚构具体机型成绩。

报告写明设备型号、系统和浏览器、内存、温度、样本与编码、重复次数、原始数据、处理时间分布、峰值内存、临时磁盘峰值、电量变化、失败及人工修正成本；覆盖连续多次处理、低电量、过热和恢复，不能只报告一次短样本。冷启动与热缓存分开；自动分析质量与作者修正后的成功率分开；隐私残留和错误合并不被平均值掩盖。

## 7 前端与文案质量门槛

### 7.1 页面职责

项目页用于继续和新建；编辑器用于改步骤、热点与分支；检查页用于定位阻断项；交付页用于选择交付物和确认后果。页面说明写“需要做什么、当前状态、下一步”，不放“一键赋能”“无限可能”“全自动精准复刻”等宣传或无法证明的承诺。

有用的首次引导、空态提示、操作说明和错误帮助应保留；禁止宣传文案不等于删除必要信息。README 可以事实性介绍产品、用法、限制与开发状态，不使用无证据的性能、隐私或创新断言。

设计评审必须包含：真实信息层级、操作优先级、状态转换、错误恢复、触控范围、长文案、长项目名、空数据和容量边界。开发截图必须来自实际运行版本，不能用设计稿代替实现证据。

### 7.2 数据与按钮真实性

- 新用户初始项目数为 0，不自动伪造最近项目、发布数或成功率。
- 可内置独立“示例项目”，明确样例来源与用途；样例不计入真实统计，不假装是用户上传或 AI 实时生成。
- 处理进度来自真实阶段；未知总耗时用阶段说明或不定进度，不虚构 99%。
- 保存完成仅在持久化成功后显示；撤销链接仅在服务器确认后显示成功。
- 未支持功能不放可点击占位入口。可以在帮助中说明范围；不能用“即将上线”按钮填补产品页面。
- 网络、权限、存储、分析、格式和复核错误分别给出原因、保留了什么以及能做什么。

示例文案：

- “无法导入：这段视频使用了当前不支持的编码。请重新录制为受支持格式，或改用截图。”
- “空间不足，导出已停止。已保存的项目仍可编辑；清理空间后可重试。”
- “遮挡已修改，这段视频需要重新检查。”
- “撤销尚未完成。设备当前离线，链接仍可能可访问；联网后请重试。”
- “缺少素材，无法发布。打开步骤 6 重新选择画面。”

错误码供定位，用户文案仍可读；不得向界面暴露栈、密钥、完整文件路径或内部服务地址。

### 7.3 可访问性与国际化

触控目标遵循产品规格至少 48 dp；拥挤画面提供文字动作列表，而不是扩大热点后遮住其他动作。热点和图标有语义标签，读屏顺序与视觉顺序一致；Web 支持键盘与可见焦点。状态和风险不只用颜色表达；缩放、字体放大和较长文案不遮住关键操作。

视频可暂停和跳过到已定义结果，提供减少不必要动效的路径。只用文字选项也能走完主路径与分支。无障碍检查结合自动检查、TalkBack/浏览器键盘与人工场景，不能仅凭分数宣称合规。

P0 以中文交互为基线，字符串资源化，禁止在组件中散落用户可见硬编码文案；时间、日期、数字和文件容量格式集中处理。测试中文长文本与伪本地化，预留扩展和换行。内部 ID、错误码、schema 字段不本地化；外语版本只有完成内容与行为验收才可宣称支持。

## 8 隐私 安全与数据生命周期

### 8.1 数据边界

维护一张数据流图，区分原素材、草稿、候选 OCR、安全派生资产、不可变版本、托管记录、账号及安全日志。每项注明产生地、读取者、存储位置、是否可出设备、删除与备份规则。

- 本地路径与网络路径显式分离；未主动发布或交付给外部服务时不能上传素材。
- 限定具体文件授权，不申请与任务无关的通讯录、广泛照片或无障碍服务权限。
- 源素材、OCR、敏感缓存和草稿按规格排除系统云备份及相关迁移范围，并实际验证系统行为；自动保存只解决中断，不声称防卸载和丢机。
- 所有导入包、AI JSON、文本标签和资源名均视为不可信数据，不能执行包内脚本、动态 import、表达式或提示指令。
- 解包在隔离临时目录验证后原子进入库；大小与文件类型不能只信扩展名或 manifest。
- 交付/观看预览、对外封面、截图和裁片只引用对应安全资产；失败时不得回取原片兜底。编辑器的来源回看与遮挡编辑可以访问本机私有原素材，但与交付/观看域明确隔离；项目首页尚无合格安全封面时显示中性占位，不外露未脱敏帧。
- 服务器仅接收主动发布且已复核的安全产物；管理鉴权不能只靠前端按钮隐藏或难猜 URL。

### 8.2 隐私证明的边界

自动扫描不是“安全证明”。隐私通过必须同时有输出重解码、文件清单验证、针对已知测试线索的检测、逐段人工审阅及内容摘要绑定记录。测试用假电话、假地址和测试音轨；生产素材不得为验证而复制到公共仓库。

撤销阻止后续新请求，不能收回已下载、截图或离线副本。说明必须在交付确认中呈现。缓存、CDN、缩略图、转码结果和备份删除策略一起设计，不能只撤销 HTML 页面。

### 8.3 secrets 与第三方服务

仓库、提案、错误报告、AI 输入和日志不得出现访问令牌、验证码、私钥、签名密钥、真实邮件凭据或 .env 内容。示例文件只留占位值。秘密扫描覆盖提交与发布制品；GitHub 付费安全功能的可用性另查，可使用审核过的独立 CI 扫描器，但不能写“已启用”而未运行。

发布签名与生产凭据独立保管，最小权限、可轮换、有恢复负责人。泄漏先失效/轮换，再清理痕迹与调查，删除一个 Git 文件不能使泄漏失效。新增服务需记录数据接收方、用途、区域/保留政策、费用、权限和故障退路；未批准不静默切换云 AI。

## 9 可观测性 迁移与恢复

### 9.1 最少但够用的观测

本地任务用明确状态机记录任务 ID、阶段、进度、重试次数、耗时、结果码、输入版本/内容摘要和安全的关联 ID。云侧记录发布提交、访问拒绝、到期、撤销和管理操作。ID 避免使用邮箱、手机号或素材正文。

不得记录原画面、OCR 全文、源文件路径、验证码、认证 token、带访问凭据的完整 URL。崩溃报告要过滤上下文；诊断上传必须由明确的数据政策和用户选择覆盖，P0 不因引入监控 SDK 自动外传本地素材。观看统计属于后续范围，不混在“可观测性”中默认采集。

进入托管开发前冻结最低运维指标：发布失败率、任务积压、访问拒绝异常、撤销失败、对象存储错误及延迟；设置可行动告警、责任人、日志访问控制和保留期限。当前不编造 SLA/SLO 或“已监控”。每个告警要有操作手册与验证方式。

### 9.2 版本与迁移

应用版本、数据库 schemaVersion、交换包 schemaVersion、adapterVersion 和用户发布 releaseId 分开管理。任何影响读取或语义的更改都要兼容矩阵；未知主版本明确拒绝，不默默丢字段。

数据库迁移使用事务和可验证中间状态；旧样例数据库必须跑升级、中断恢复与重复执行测试。服务端优先扩展后收缩，客户端与服务至少覆盖声明支持的兼容窗口。删除字段或破坏性迁移单独 PR，写清备份、停机/只读需求、不可逆后果和前向恢复方案。

数据回退不等于二进制回退。若新数据无法被旧版读取，不能直接安装旧版并承诺恢复；先确认兼容性，必要时前向修复。复核标记、撤销和过期状态不能在迁移或恢复后被错误复活。

### 9.3 备份恢复边界

本地草稿不做首版自动云备份；用户导出的脱敏包也不等于完整源工程备份，文案和帮助必须说明。

托管端仅备份实际持有的安全资产、发布记录与必要账号数据。上线前确定备份加密、权限、保留与删除政策、RPO/RTO 目标及负责人。必须在隔离环境实际恢复一次，验证账号管理、版本内容、到期和撤销状态、资产完整性；恢复后默认保守拒绝不确定访问。不得让旧备份重新公开已撤销内容。

有备份任务的绿色记录不等于可恢复。恢复演练报告写实际耗时、数据缺口和操作步骤；没有报告就不宣称已具备灾难恢复能力。

## 10 依赖 许可证与 AI 代码责任

### 10.1 供应链

依赖新增必须说明必要性、维护状态、许可、体积、运行时权限、离线能力与替代方案。固定直接与传递依赖，提交锁文件；构建工具、SDK、容器、Action、OCR 模型、媒体库、字体和图标均纳入清单。定期升级通过独立 PR 及相关回归，不能自动把大版本升级合进 main。

每个发布候选生成与具体提交/制品绑定的 SBOM，至少涵盖实际打包的依赖和版本；Android、Web、服务端、Remotion 模板分别覆盖。GitHub 可从依赖图导出 SPDX SBOM，但它不是所有媒体、模型、字体和运行制品的完整证明，项目需补齐非包管理资产与构建产物信息。[GitHub SBOM 导出说明](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/establish-provenance-and-integrity/export-dependencies-as-sbom)

发布时附第三方许可/NOTICE，核对模型、字体、图标、编解码器与 Remotion 的当前许可及实际使用方式；不能把“可下载”当允许商用或再分发。本仓库现有 [LICENSE](../../LICENSE) 为用户初始化的 Apache-2.0，本 PR 原样保留；这不自动决定第三方依赖、模型、素材或 Remotion 的许可，仍需逐项核对。未来项目许可变更由权利人明确决定。未知许可、来源不明、与分发条件冲突的组件阻断发布。

### 10.2 AI 辅助变更

- 每个 PR 有一位真实责任人，负责理解最终差异、测试结果、许可和安全后果；AI 产出不转移责任。
- AI 协助范围与真实归因保留在提交历史或必要测试/审查记录，不要求每个 PR 正文重复工具版本、复核清单和未验证项。不保存包含用户秘密或无关隐私的完整提示。
- AI 生成的接口、库用法、引用、测试成绩必须验证；不存在的 API、假测试和猜测结果不进入主干。
- 使用 AI 做另一轮审查可以提高发现率，但要标为 AI 辅助审查，不等同独立人类批准，也不保证代码安全。
- 不伪造作者、Co-authored-by、签名或审查身份；按实际工具和仓库政策归因。AI 生成不表示自动获得第三方版权授权，疑似大段复现先核查来源。
- 不把未经授权的用户源素材、密钥或真实隐私送进外部模型；测试夹具和上下文按最小必要范围提供。
- 参赛或对外披露按实际贡献和当届要求，保留真实提交史与贡献记录，不虚构开发时间或纯人工原创。

## 11 发布与回滚

### 11.1 版本候选必须包含

- 固定提交、应用版本、schema/adapter 版本、构建环境、制品哈希与签名状态。
- 从需求 ID 到 PR、测试和版本的完整映射；A01–A16 的实际结果和未完成项。
- Android 真机、Web 兼容、真离线、Remotion 实际渲染与 JSON 回写报告。
- 安全/隐私阻断清零，许可证与 SBOM 完整，迁移/恢复演练通过。
- 用户可见变更、准确限制、安装/升级方式及隐私说明。
- 发布负责人、可观测指标、暂停条件、回滚路径和验证脚本/操作清单。

只有全部 P0 满足才称“符合产品规格 v0.1 的完整首版”。此前可发布经过验收、范围明确且独立有用的窄切片，发布范围经 proposal PR 接受，并保留完整产品目标的未完成记录。每个切片都须有真实闭环、可靠失败处理和适用于该范围的安全隐私门禁；alpha 或预览标签不能豁免这些底线。

### 11.2 发布执行

只从固定、受控的版本候选发布制品，避免不同环境各自随意重建。开发、预发布和生产数据与权限隔离；生产上线、签名分发、域名和收费服务开通由授权责任人确认。合并 PR 不自动授权这些动作。

先在预发布验证新建、编辑、脱敏、离线包、托管与撤销，再按选定平台的小范围分发机制观察。具体观测窗口、阈值和人选在发布前冻结，不写没有资源支撑的 7×24 承诺。

严重隐私泄漏、鉴权旁路、用户数据损坏、无法恢复的主路径失败触发停止发布。应先限制继续扩散，再确定回退或前向修复；保留必要且脱敏的证据并通知受影响方，不能把日志清空当事故解决。

### 11.3 回滚操作

服务回退使用上一已验证制品，确认 schema 仍兼容；不兼容时优先关闭相关入口/只读及前向修复，不盲目还原数据库。Android 已分发版本不能承诺远程降级所有设备，应准备停止继续分发和修复版本。

用户已经发布的演示是不可变内容，程序回滚不允许覆盖它们。撤销演示、删除资产和回退服务是不同动作；旧链接不得因为回退重新生效，已下载离线包无法收回。

每次发布后记录实际制品、时间、操作者、验证结果和观察结论。回滚后重新走新建或观看关键路径、直接媒体访问、到期撤销与任务恢复测试，并补事故回顾和回归用例。

## 13 可直接采用的模板

以下为规范中的模板要求；可复制文件见 [模板索引](../templates/README.md)，GitHub PR 模板已落位。模板内容不代表真实 Issue、测试或接受记录。

### Proposal 或 RFC 模板

```text
标题：需求 ID + 本次要解决的问题
状态：Draft / Proposed / Accepted / Superseded
负责人：真实姓名或已核实账号
关联：产品需求、Issue、相关 PR 和 ADR

1. 问题与使用场景
2. 本次范围与明确非目标
3. 用户行为：正常、空、失败、取消、恢复
4. 数据和接口合同：版本、坐标、限额、兼容性
5. 可选方案与取舍
6. 隐私、安全、无障碍、性能、许可影响
7. 验收条件及可重复测试输入
8. 实现拆分、依赖、迁移和回退
9. 已知事实、设计承诺、假设与待验证项
10. 接受记录：谁、何时、在哪个 PR、尚有何条件
```

### ADR 模板

```text
ADR 编号与标题
状态：Proposed / Accepted / Superseded by ADR-...
日期、真实决定者、关联需求与提案 PR
背景与约束
选择及理由
已考虑的替代方案
代价和风险
验证证据或仍待验证的条件
重审触发条件
```

### PR 模板

标题采用英文类型加中文描述，保留真实需求 ID，例如 `docs(ENG-001): 简化变更说明`。正文只写具体变更，模板中的占位内容须替换为实际内容；测试、审查、SHA 等详细证据留在 CI 日志或必要测试文档，不主动另发长核验评论。真实阻断或需要决定的问题单独简短说明。

```text
# 变更

- 说明具体变更及影响

关联：需求 ID
```
